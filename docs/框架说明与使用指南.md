# ACE_ECF_26 框架说明与使用指南（详细版）

> 适用对象：首次接入本框架的嵌入式开发同学、负责模块集成的项目维护者、需要进行功能裁剪/版本核查的成员。  
> 代码基础版本：`ACE_ECF_CPP_V1.2`（来自仓库根 README 标识）。

---

## 1. 框架定位与总体能力

ACE_ECF_26 是一个面向 RoboMaster 电控场景的 STM32 嵌入式 C/C++ 混合框架，核心目标是：

- **以模块开关方式管理功能**（便于按车型/项目裁剪）；
- **统一 BSP + Module + App + Algorithm 分层**（降低耦合）；
- **兼容 STM32F4 / STM32H7 两类主控常见工程形态**（CAN/FDCAN、USART、SPI、PWM 等）；
- **面向比赛场景提供高复用组件**（电机驱动、裁判系统、遥控器、IMU、功率控制、调试灯、日志等）。

从 `template/CMakeLists.txt` 可见，框架通过 `ADD_MODULE(USE_xxx)` 宏式能力将功能分块引入，避免“全量编译”。

---

## 2. 目录结构与分层职责

建议按下面方式理解目录：

- `Algorithm/`：算法层（PID、LQR、滤波、卡尔曼、RLS、数学工具）。
- `Bsp/`：底层外设适配层（CAN/FDCAN、USART、SPI、PWM、DWT、ADC、I2C、EXTI、FLASH）。
- `Module/`：设备/业务模块层（电机、DR16、Referee、IMU、INA226、WS2812、Servo、Log 等）。
- `App/`：应用组合层（功率控制、命令汇总、安全任务、调试灯、音乐任务等）。
- `template/`：CMake 接入模板。
- `ecf_configList.h.example`：全局宏配置示例（模块开关、外设映射、参数配置）。

### 分层依赖建议

通常依赖链应保持为：

`Algorithm <- Bsp <- Module <- App <- 用户业务(task/main)`

- Algorithm 尽量无硬件依赖；
- Bsp 只做外设收发与底层能力暴露；
- Module 封装设备协议和业务接口；
- App 负责多模块组合、系统逻辑与策略。

## 4. 框架接入与使用方法（推荐流程）

## 4.1 前置环境

建议准备：

1. `STM32CubeMX`（工程生成）  
2. `VSCode + STM32 for VSCode`（可选）  
3. `Arm GNU Toolchain`（交叉编译）  
4. 可选 `MinGW`（Windows 上 make 工具链）

> 注：仓库已有 `template/CMakeLists.txt`，可按 CMake 流程组织工程；也可按根 README 的 makefile 流程接入。

## 4.2 与 CubeMX 工程合并

1. 用 CubeMX 生成基础工程（含 HAL、启动文件、时钟与外设初始化）。
2. 将本框架目录（`Algorithm/Bsp/Module/App` 与配置头）并入工程。
3. 在构建系统中添加这些目录及源文件：
   - CMake 场景：参考 `template/CMakeLists.txt` 中 `USER_ADD_DIR` 与 `ADD_MODULE`；
   - Makefile 场景：参考根 README 的 C/C++ 混编改造说明。

## 4.3 模块开关配置（核心）

框架以 `USE_xxx` 宏作为主要开关，典型做法：

1. 在 CMake 侧打开模块（例如 `-DUSE_DR16=ON`、`-DUSE_IMU=ON`）。
2. 在 `ecf_configList.h`（由 example 复制）中补充外设句柄映射与参数宏。
3. 在业务初始化中调用对应模块 init，随后在主循环/任务中调用 update。

常见开关示例：

- `USE_DR16`
- `USE_REFEREE`
- `USE_IMU`
- `USE_DJI_MOTOR` / `USE_DM_MOTOR`
- `USE_POWER_CTRL_RLS` / `USE_POWER_CTRL_NORLS`
- `USE_DEBUG_LIGHT`
- `USE_LOCAL_FLASH_LOG`

## 4.4 F4/H7 差异注意事项

- H7 常使用 `FDCAN`；F4 常使用 `CAN`。
- `ecf_configList.h` 示例已经按 `STM32H723xx` 与 `STM32F405xx` 提供条件编译分支。
- 若切换芯片系列，需同步检查：
  - 外设句柄宏映射（如 `hfdcanx/hcanx`、`huartx`）；
  - GPIO/时钟初始化；
  - 中断优先级与 DMA 通道。

## 4.5 典型最小可运行组合

以“遥控底盘 + 电机 + 裁判系统 + IMU”为例：

1. 开启模块：`DR16`、`REFEREE`、`DJI_MOTOR`（或 `DM_MOTOR`）、`IMU`、`SINGLE_CAN`。
2. 按 `ecf_configList.h` 配置串口/CAN/FDCAN 句柄。
3. 启动顺序建议：
   - `DWT` -> `CAN/FDCAN` -> `USART/SPI/PWM` -> 各 Module init -> App 层任务。
4. 主循环/RTOS 任务中按频率调度：
   - 输入采集（DR16/referee/IMU）；
   - 控制运算（PID/LQR/Kalman）；
   - 输出执行（motor/pwm/ws2812）。

## 5. 建议的工程结构（项目侧）

建议在你的具体机器人项目中采用以下组织：

- `Core/Src/main.c(.cpp)`：系统入口、时钟、HAL 初始化。
- `User/Tasks/`：项目任务（底盘、云台、拨盘等）。
- `ACE_ECF_26/`：框架原始目录（尽量少改动，便于后续升级）。
- `ecf_configList.h`：项目级配置（必须版本管理）。
- `ProjectConfig/board_xxx.h`：板级差异参数（可选）。

这样可以做到：

- **框架与项目解耦**：业务只调接口，不侵入底层；
- **升级成本可控**：后续替换框架版本时，只需对比配置和少量适配层；
- **多人协作清晰**：算法、驱动、应用可分工并行。

## 6. 版本管理建议（强烈推荐）

当前仓库中部分模块版本号风格并不统一（如 `V1.0`、`v26.x.x.x`、未标注）。建议后续统一为：

- 统一语义化版本：`MAJOR.MINOR.PATCH`；
- 每个模块主文件都维护 changelog 注释；
- 在仓库新增 `docs/module_version_matrix.md` 自动汇总版本；
- 版本变更与接口变更一同记录（特别是 CAN 协议字段、裁判系统协议结构体）。

## 7. 常见问题与排查建议

1. **编译不过（C/C++ 混编）**  
   - 检查构建系统是否把 `.cpp/.hpp` 纳入；
   - 检查 C++ 标准（建议 C++14 或以上）。

2. **H7 FDCAN BusOff 恢复异常**  
   - 优先核对 `Bsp/CAN/fdcan` 当前版本实现是否已启用恢复逻辑；
   - 检查硬件终端电阻、波特率、时序参数。

3. **模块已开但无数据**  
   - 检查 `USE_xxx` 是否在编译命令中生效；
   - 检查 `ecf_configList.h` 句柄映射是否与 CubeMX 生成名称一致。

4. **裁判系统/遥控器串口冲突**  
   - 明确每个模块独占 UART；
   - DMA + 中断优先级避免抢占死锁。

## 8. 维护者快速检查清单

每次新项目接入，至少核对：

- [ ] 芯片型号与 `CAN/FDCAN` 分支是否匹配
- [ ] `ecf_configList.h` 是否完整且句柄正确
- [ ] 关键模块版本是否满足项目需求
- [ ] 功率控制策略（RLS / noRLS）是否与底盘类型一致
- [ ] 裁判系统协议版本是否与赛季规则一致
- [ ] `safe_task` 保护逻辑是否已启用

## 9. 结语

本框架已经具备“可快速拼装机器人电控系统”的能力。对于实际项目，建议采用“先最小系统跑通，再逐模块开启”的方式推进，并把**模块版本矩阵 + 板级配置**作为交付文档的一部分长期维护。
